# 逐气泡发送延迟 · 设计备忘

日期：2026-11-25

适用版本：`1.0.1`（首版接入于 rc62）。已接入私聊投递和 Koishi 专属配置中心。

## 为什么要做

真人聊天时，会先发一两句，停下来想一会儿，再补充、修正，甚至反驳刚才的话。就算剧本写出了这段停顿，如果实际投递把几句话连着发出，用户也感受不到这个过程。逐气泡延迟是为了把这种**边聊边想的节奏**变成实际可见的消息间隔，而不是只留在剧本里。停多久由写作模型随每个气泡一起给出；不需要停顿时就是 `0`。

## 首版范围与写作中立

首版只覆盖**由新私聊触发的当前私聊即时文本回复**中的单泡和多泡。主动私聊、群聊发送、群背景、未来定时发送（`sendAt`）及其他渠道的规则不变。这里的「即时发送」是指主角在当前场景已经作出发送动作，不代表宿主必须在零秒内投递。

**先照常写，再给已有气泡标延迟。** 逐泡延迟是投递元数据，不是写作目标。措辞、篇幅和是否分泡仍由场景决定；不要为了填写延迟而加写停顿、拉长回复或拆出更多气泡。没有明确停顿就填 `0`，不要求写出时间说明。模型只给出场景需要的等待，不估算自己的输出耗时或宿主的模拟打字时间。

## 输出合约与提示词

保留现有私聊发送动作、正文绑定和分泡规则。在每个适用的发送动作上新增 `bubbleDelaySeconds`，按该动作的气泡顺序一一对应。比如某个已有双泡动作可给 `[0, 4]`；正常的单泡也必须给一个值，例如 `[0]`。没有发送动作就没有该字段。值必须是有限的非负秒数；数组长度必须等于按当前分泡配置实际解析出的气泡数。关闭分泡时按一个气泡校验。

校验在任何投递之前完成。缺失、非法或数量不匹配时进入输出校验与修复；修复仍未通过，不投递该无效动作，不静默补 `0`、错配或合并气泡。旧合约与不属于首版范围的发送继续走现有路径，不要求补填。

实际提示词只在私聊输出合约旁加一小句，保留原有写作指导和分泡规则，并去掉适用路径中「首泡立即发送」的旧表述。不需要向模型解释宿主的计时公式。拟用说明：

> For each private-message bubble you would already write, give one delay in seconds in `bubbleDelaySeconds`, in bubble order. Use `0` when there is no distinct pause. Do not change the wording or split a message just to add a delay.

## 延迟如何计算

设 `Dᵢ` 为模型为第 `i` 泡标的延迟，`Tᵢ` 为宿主对该泡估算的模拟打字时长，两者统一单位后取最大值，**不相加**。`0` 只表示模型没要求停顿，不取消现有打字下限。

- **首泡**：`t₀` 是本轮叙事请求发起时刻，`L` 是从 `t₀` 到完整输出可校验且通过校验时的已用时间。首泡最早在 `t₀ + max(L, D₁, T₁)` 发送，即结果可用后只补等 `max(0, max(D₁, T₁) - L)`。如果随后才进入投递调度，期间已经过去的时间也不用重等。
- **后续泡**：以上一泡实际成功投递的时刻为起点，等待 `max(Dᵢ, Tᵢ)`。上一泡因平台或调度原因晚发，后续间隔不因此缩短。不抵扣本轮的模型耗时，也不从首泡开始累计预排。

例如，完整结果在请求开始后第 8 秒可用，暂不计平台传输耗时：

| 气泡 | 模型给出的延迟 | 模拟打字 | 相对请求开始的最早发送时刻 |
| --- | ---: | ---: | ---: |
| 第 1 泡 | 20 秒 | 15 秒 | 20 秒（结果可用后再等 12 秒） |
| 第 2 泡 | 10 秒 | 3 秒 | 30 秒 |
| 第 3 泡 | 0 秒 | 2 秒 | 32 秒 |
| 第 4 泡 | 20 秒 | 4 秒 | 52 秒 |

若首泡的同一结果不是第 8 秒，而是第 25 秒才可用，首泡在结果可用后无需再等。

## 投递调度

1. **先拿到完整合约，再开始投递。** 适用的私聊发送不走提前投递（early reply）；模型请求本身可以继续流式返回。`requestStartedAt` 是现有的首泡计时接入点，不以流式首字到达或首泡投递任务入队的时刻代替。
2. **整组待发气泡都能被打断，但只放行当前一泡。** 正式剧本、剧本中的投递账本和整组 `split-message` 计划在同一数据库事务中提交。提交成功后登记本轮已提交状态、实时会话路由、计时器与回忆缓存。模型请求与平台投递都在事务外。计划按发送动作和泡序号关联账本，首泡等待期间也能被查到并取消。收到上一泡的平台成功结果后，再让下一泡进入计时；这是平台投递成功，不是等用户已读。前一泡失败或结果未知时，不把它当作已发来放行后一泡。
3. **等待不占用叙事锁。** 模拟打字时长每泡只计算一次，已算出的间隔或到期时刻在调度重试时沿用，不重新抽随机浮动。到期只是具备投递资格，现有权限、端点检查和取消检查仍然有效。

## 等待期间收到新私聊

如果同一私聊里用户发来新消息，而上一轮还有气泡在等着发送，**宿主立即停止旧回复的等待，取消所有尚未交给平台的气泡，并用新消息发起一轮新的剧本推进**。不必等旧计时结束，首泡还没发出时也一样。投递前最后一次检查该组是否已被打断；已经交给平台的气泡不能保证撤回，按平台返回的实际结果记账，不能预先认定为已发，也不能当成确定未发的草稿。已经确认发出的气泡保留。取消后，按原有意图白名单重设故事级最早唤醒，覆盖其他参与者已经到期的任务。常规唤醒补排仍查询未来任务。

## 下一轮怎样收到打断上下文

沿用 `split-message` → `supersededIntents` → `interruptedOutgoingDrafts` 的交接路径。现有投影是一泡一条，并把每条都描述成「还没打完字」；新版按**同一个被打断的发送动作**归组，只记录确定发生的事情。新私聊的正文仍只放在 `currentEvent`，已发对话仍由 `recentScript` 和 `deliveryReality` 提供；不把打断另立成一个需要排序的事件。

每组打断记录包含：

- **打断发生时。** 以最先取消该组待发气泡的那条已接受私聊的实际入站时间为准，不用模型请求开始时间。同批有多条时，用 `triggerMessageIndex`（从 1 开始）指向具体消息；序号由宿主从合并前的入站记录关联，不从合并后的正文猜测。带打断记录的多条批次在 `currentEvent` 中保留可辨识的逐条边界和序号，不另抄一份消息正文。合并或重排不会把打断改归给更晚的消息。
- **已经发到哪一泡。** `deliveredBubbleIndexes` 给出组内已确认投递的泡序号，正文沿用已发对话记录，通过 `sourceAction` 关联原发送动作。相关的已发片段如果被上下文裁剪掉，在本轮补上必要的原文和投递状态，避免留下空引用。首泡就被打断时，这个数组为空。平台确认投递不表示用户已读，也不表示一定早于新消息；如需判断先后，以投递记录与入站时间为准。
- **还没发什么。** `cancelledBubbles` 按原发送顺序给出每个确定未交给平台、已取消气泡的序号和原文。使用「原本还想发，但新消息先到了」的口径，不推断她是在思考、已经打到一半，还是根本还没开始输入。
- **有一泡已经交给平台，但尚无确定结果时。** 不等回执才启动新一轮；该泡不列入已发，也不列入已取消草稿。用 `deliveryReality` 标明结果未确认，有结果后以账本为准，不补发已取消的后续泡。

例如，主角已经发出「那就明天吧」，本想再补「等等，我明天晚上好像有事」，这时用户先发来「明天不行，周五呢？」。下一轮相关上下文示意如下（只展示相关字段，`sourceAction` 是对现有投递动作的引用）：

```json
{
  "currentEvent": {
    "type": "private-message-batch",
    "content": "明天不行，周五呢？"
  },
  "interruptedOutgoingDrafts": [
    {
      "sourceAction": { "commitId": "turn-42", "eventId": "reply-1", "scriptEntryId": 81 },
      "interruptedAt": "2026-11-25T21:10:12+08:00",
      "triggerMessageIndex": 1,
      "deliveredBubbleIndexes": [1],
      "cancelledBubbles": [
        { "bubbleIndex": 2, "content": "等等，我明天晚上好像有事" }
      ]
    }
  ]
}
```

这里用于模型阅读的泡序号从 1 开始，映射到现有账本的索引即可，不改账本索引。交接只跟随触发它的私聊批次；该批次在同一次推进内修复输出、或因新消息到达而回队合并时保留记录，同一动作和气泡不重复投影。新推进成功提交后不再把同一记录作为后续回合的新打断反复发给模型。

**区分模型还在生成与气泡已经在等待。** 如果新消息到达时，旧请求还在流式生成、没有形成经校验且已登记的待发送动作，则旧请求按现有回合失效逻辑处理。下一轮照常接收新消息；不把模型输出的半截文本当作主角已写好或正在输入的草稿，也不构造这类打断记录。

提示词只需替换现有私聊相位里对 `interruptedOutgoingDrafts` 的简短说明；草稿出现不代表主角已察觉或读了新消息，也不要求剧本每次复述被打断的经过。拟用说明：

> `interruptedOutgoingDrafts` records what she meant to send before an incoming message interrupted the outgoing sequence. Only confirmed deliveries count as messages she sent. Cancelled text is a private intention, not something the user received or a message to resume automatically. Continue from the scene as it now stands; whether she notices the new message or still wants to say any of it is left to the scene.

恢复扫描发现旧版本遗留的私聊逐泡账本仍有待发气泡、却缺少对应计划时，每个发送动作在本进程内告警一次。账本保留原状，通用投递补偿跳过该动作。

## 首版验收重点

- 单泡也必须给值；`[0]` 合法，但打字下限仍生效；缺失或数量错配不能提前发出任何该动作的气泡。
- 模型产出较慢时首泡不再补等；较快时只补差额。后续泡按前一泡成功发出的时间计算，尤其要验证上一泡晚发时不会挤掉下一泡的间隔。
- 新私聊在首泡等待或两泡之间到达，都能取消尚未交给平台的整组余量，新回合能获得原文；到期与入站相遇时，已交平台和可取消的部分按上述边界分别处理。
- 首泡尚未投递、已发部分气泡、平台结果未确认、批次合并与重试，以及仅模型流式生成被打断，分别验证下一轮看到的内容；不把未确认或半截输出当成已发或确定被取消的草稿。
- 提示词样例以正常单泡和 `0` 为主，不把多泡、长停顿当作示范目标。群聊与 `sendAt` 原有行为不变。

独立的后台 `narrative-retry` 仍是现有到期推进路径，不重放上一轮私聊批次，也不把旧打断草稿当成新的入站事件。本地插件构建通过后，下次加载该工作区的 Koishi 会读取新版；不代表已在其它或正在运行的 Koishi 实例部署。
