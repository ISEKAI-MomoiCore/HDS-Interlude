## 第一轮实现约定

1. **模块加载**：Console 前端输出带默认导出的 ES 模块，外部依赖交由 Koishi Console 解析；服务端同时登记样式。发布前校验覆盖前端产物，支持维护者按项目约定重建。
2. **任务与内容代次**：暂停使旧任务退休，已获平台确认的内容仍可记账；故事重置/清空使旧内容代次退休，旧回执和旧派生状态随之撤回。群消息、反应、贴纸和原生表情沿用这一口径。
3. **资料生命周期**：案头为故事级短期资料。故事清理移除相应案头并过滤排队考据；全库清理清空全部案头与队列；范围清理采用保守撤下该故事案头的方式等待重新考据。网络结果在提交前核验任务有效性。
4. **验证范围**：采用下文“各轮通用验收约定”，第一轮的具体执行结果记录于验收表。

## 实施范围与依赖

### 第二轮 2A：清理兜底与数据范围（F05/F04）

`src/database.ts` 的 21 个 model 均已声明主键。F05 的修复位置是 `src/service.ts` 的 `clearDatabase`：依据已有 schema 选择 `id`、`storyId`、`endpointId` 或 `aliasStoryId`，并建立逐表合法载荷。`interlude_long_arc_progress` 使用 `storyId`；overlay、长线指导/进度各有独立字段，scene/arc 也分别处理。此处采用完整表分发，使清理范围和兜底范围能够同步核对。

F05 先行或与 F04 同步完成，再将空间记录、作品数据接入故事清空和全库清空。正常物理删除与删除失败后的逻辑清理共用清理契约。故事清空继续保留现有空故事与参与者重建行为；平台清空、全部故事重置等委托入口同步覆盖目标故事。

| 数据 | 本轮约定 | 验收重点 |
|---|---|---|
| `interlude_qzone_post` | 按故事或全局范围清理空间发布内容与动作追踪 | 删除成功与逻辑兜底都撤下旧内容；若产品确需跨重置限流，单独保存最小计数/时间信息并说明用途 |
| `interlude_work` | 纳入 F04，清理目标故事的作品正文、版本、提案及任务 | 其他故事隔离；逻辑载荷符合作品读取约束；旧生成任务返回后保持已清空状态；删除后重建的新作品保持独立 |
| `interlude_sticker` | 故事重置与本轮全库运行数据清理保留全局可复用资产索引 | 代码注释及清空入口说明保留范围，验证故事清理后资产仍可正常读取 |

SharedWorks 当前具有纯模块、数据库表及测试，service/narrator 生产接线仍处于暂缓状态（见 `docs/CHANGELOG.md`、`docs/development/PLUGIN_UPGRADE_EXECUTION_PLAN.md`）。作品表纳入清理属于实验/历史数据卫生与未来接线约束，其当前状态继续按实验模块记录。作品异步生成会重读任务 ID 并通过 generation 执行 CAS；回归应核对清空、逻辑兜底及删除后重建三种情况，验证旧任务的失效边界。

表情索引来自配置目录的扫描，包含文件路径、描述和 embedding，属于全局资产。独立的资产清理流程应同时说明索引、源文件、采集缓存及扫描重建行为；本轮在清空入口明确保留语义，并将彻底移除资产作为独立管理操作记录。

### 第二轮 2B：天气来源与生命周期（F06/F07）

天气继续使用 seeded-event 队列。消费入口依据事件来源和相应开关决定资格，使天气与模型播种分别遵循配置；验证“天气开启、播种关闭”和“天气开启、播种模型不可用”，同时覆盖各来源关闭后的行为。

天气 runner 复用 `src/task-lifecycle.ts` 的代次捕获与复核，在网络返回、进入串行段和写入前核验有效性。去重依据故事、地点与有效天气事件，覆盖重置后恢复同文天气、切换故事/地点及旧事件失效。暂停/快速恢复沿用第一轮任务退休约定。

天气事件固定为 `importance: 'low'`。验收使用允许低重要性事件的推进相位，或显式调用 `drainDueSeededEvents(..., true)`；用户消息相位对 low 的过滤另作保留行为验收。

### 第二轮 2C：离线补拉账号与采集语义（F08/F09）

按端点与账号确定 Bot，并以所选账号的 selfId 判断 @、引用及自身消息。账号解析修复会激活此前被跳过的补拉路径，F08/F09 在同一子批次交付。定向采集复用在线入口的策略，覆盖 directed/background/off、合法 @/引用/媒体、自身消息和多账号场景。

账号或历史接口不可用时通过现有诊断日志说明跳过原因，便于定位端点与平台能力问题。补拉经过网络等待后，故事和任务有效性也纳入写入前复核的验收范围。

### 第三轮补充：私聊防抖与两套配置页（F11/F13）

F11 同时覆盖 `src/service.ts` 的群聊缓冲和 `src/turn-engine.ts` 的私聊缓冲。最大等待约束当前待处理批次在请求开始前的防抖推迟；批次被取走后重新计算下一批的起点。在途请求、故事串行忙碌和暂停仍遵循既有调度规则，分别验证恢复后的及时处理与批次边界。私聊首条回复提交前的请求替换及提交后的行为沿用现有语义。第三轮实际采用的批次等待上限为：群聊 3000ms；私聊为 max(3000ms, userMessageDebounceSeconds × 1000)。私聊 0 秒继续表达关闭合并，较长等待值按原配置生效。

F13 同时覆盖 `client/src/pages/ConfigCenterPage.vue` 和遗留的 `client/src/pages/ConfigPage.vue`。读取结果、异常、loading 收尾及保存后重读都校验请求归属；表单成功读取后开放保存，保存捕获目标节和数据快照。覆盖 A/B 乱序返回、旧请求失败、当前请求失败、保存期间切节及保存回执返回时的界面归属。
