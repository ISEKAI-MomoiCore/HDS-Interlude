# 平台感知设计（Platform Awareness · F1）

文档性质：多平台语义层的首个功能增量。**状态：设计 v1 待评审，未实施**。基线：`1.0.1-rc59` 工作区（2026-10-30），前置依赖 [NARRATIVE_PLATFORM_DECOUPLING_DESIGN.md](NARRATIVE_PLATFORM_DECOUPLING_DESIGN.md)（D0–D4 已全部实施）。与解耦系列不同，**本设计是功能演进**——会改变多平台场景的合约内容，不属于行为不变切片。

> 一句话定位：不给模型写"何时选哪个平台"的决策规则，只给它每个平台的**性格卡片**——选择行为交给已有的写作纪律（对等回复为默认、切换需剧本动机、同内容不双发），由模型基于"卡片 × 关系状态 × 当前剧本"自行演绎。

---

## 0. 结论摘要

- **要解决**：模型选平台时看到的是一排裸传输端点（`NarrativeEndpointOption` 只有 endpointId/targetId/channelKind/conversationKind/online 五个技术字段），零社交语义——它无法像人一样"因为这事适合在微信说"而选择通道。
- **解法**：PlatformProfile 性格卡片（她对平台的认知 + 能力面标签）随端点列表注入；三条既有选择纪律一字不动。
- **成本**：每个多平台回合约 30–50 token/平台；单平台部署零注入零变化。
- **行为边界**：QQ 单平台合约**逐字节不变**（现有快照测试天然覆盖）；QQ+微信双平台合约新增 profile 字段与一句话（快照基线需更新并记 CHANGELOG）。

## 1. 背景与动机

多平台传输选择机制（`MULTI-PLATFORM TRANSPORT SELECTION` 合约段 + `availableOutgoingEndpoints` + `endpointId` 回传）自 M4 起已平台中立，但它把平台当作**同质的管道**。而人对 IM 平台的 选择从来不只看"对方在不在线"：

- 关系：这事跟谁有关——熟人闲聊自然落在 QQ，郑重的道歉落在微信；
- 方便：语音/文件/表情包在哪边更顺手；
- 偏好：她自己就是"微信只回工作，废话都在 QQ 说"的人；
- 对等：对方用哪个平台找她，她就回哪个平台（现有合约的默认规则）。

前三种动机是**人感知到平台性格后自然产生的判断**，不是可枚举的规则。把动机写成决策表会产生 checklist 式选平台，丧失"她像人一样挑通道"的质感。HDSI 自身的哲学已经给出答案："计划只约束合理性，真实剧情始终优先"——所以只补感知，不加决策。

## 2. 现状审计

| 项 | 现状 | 出处 |
| --- | --- | --- |
| 端点列表项 | `{ endpointId, targetId, targetKind, channelKind, conversationKind, online }`——纯技术 | types.ts `NarrativeEndpointOption` |
| 选择纪律 | ①默认在哪听到在哪回 ②切换需剧本中可见的自然动机 ③同内容不双发 | narrator.ts 传输选择段与 CHANNELS 段 |
| 平台词汇 | 已参数化（PlatformWording，D2.5）——解决"措辞点名 QQ"，不提供"平台是什么"的语义 | narrator.ts |
| 能力快照 | 回合级 `chatCapabilities`（本回合可用动作），非按平台对比视图 | D2 端口 |
| 平台认知数据 | **不存在** | — |

结论：管线就绪（词汇注入点、端点选择机制、能力协商雏形都在），缺的只是一份数据和一处注入。

## 3. 设计

### 3.1 PlatformProfile：每平台一张性格卡片

```ts
interface PlatformProfile {
  /** 她眼里这个平台是什么——一到两句话的角色化认知，非功能说明。 */
  character: string
  /** 能力面标签（人类可读）：语音、表情包、贴纸、消息反应、文件……
   * 数据源与 D2 能力快照同源——一份事实两种视图。 */
  affordances: string[]
}
```

默认卡片由**平台适配器内置**（D0–D4 的 PlatformAdapter 体系）：

```
qq:       { character: "熟人日常闲聊的地方，语音和表情包很自然，随口就能回",
             affordances: ["语音", "本地表情包", "消息反应", "原生表情"] }
wechat:   { character: "偏正式一些，家人同事都在，措辞会更规矩",
             affordances: ["语音", "贴纸"] }
telegram: { character: "……", affordances: […] }   // 未来由 TelegramAdapter 提供
```

**Console 可覆写**：`character` 是角色设定的延伸（同一个角色在不同部署里对平台的认知可以不同），默认值只是起点。覆写层级见 §7 开放问题。

### 3.2 注入点：把裸端点变成"有性格的通道"

- `NarrativeEndpointOption` 增加可选字段 `platformProfile?: PlatformProfile`；
- 传输选择段增加一句话："platform profiles describe how she perceives each channel — context for her choice, not commands"；
- **单平台不注入**（没有选择就没有感知的必要），与 specializationAutoTrim 的裁剪哲学一致——单平台部署 token 与行为零变化。

### 3.3 选择纪律：三条既有规则一字不动

动机枚举**明确排除**在合约之外。防乱跳与防重复由既有通用约束兜底（它们恰好覆盖全部动机类型的边界）：切换需要剧本可见动机（防随意跳）、不双发（防重复）、默认对等（防失礼）。至于"此刻她为什么选这个平台"——交给模型基于性格卡片与关系状态演绎，剧本本身就是动机的可追溯载体。

### 3.4 与 PlatformWording（D2.5）的关系

两者都来自适配器、都描述平台，但分工不同：**wording 是措辞**（合约规则怎么称呼平台/表情/标签），**profile 是语义**（平台在她生活里是什么）。建议实施时统一为适配器导出的单一 descriptor（`{ wording, profile }`），一次注入两个面——避免将来两个入口各自演化。

### 3.5 跨平台"反应相似"的定义

同输入下模型的**语义动作集合**一致（回复文本、reply 模式、引用、延迟）；平台差异只允许出现在两处——**能力可用性**（profile/能力快照协商出的动作面）与**渲染**（语义 → 平台工件映射，如 `like` → QQ 表情回应 / TG reaction）。F1 的 affordances 标签让模型在多平台回合中具备对比视野，是这一定义的感知基础。

## 4. 配置面

| 层 | 来源 | 说明 |
| --- | --- | --- |
| 默认 | 适配器内置 | 每平台一份，随插件版本演进 |
| 覆写 | Console（P1 配置中心后续节或独立小节） | `platformProfiles: Record<platform, string>`——仅覆写 character 文本；affordances 由适配器按实际能力报告，**不接受覆写**（能力是事实不是人设） |

## 5. 验证与门槛

1. **QQ 单平台逐字节不变**：现有六场景合约快照测试天然覆盖（profile 不注入），零改动必须全绿——这是硬门槛。
2. **双平台快照新基线**：QQ+微信场景的合约因新增 profile 字段与一句话而变化——更新快照基线并在 CHANGELOG 明示（这是本设计唯一的行为变化点）。
3. **注入正确性测试**：多平台注入/单平台不注入/Console 覆写生效/未知平台回退适配器默认。
4. **质量观察（非门槛）**：modelCapture A/B 对比注入前后的平台选择分布与切换动机的剧本呈现——用于调卡片文案，不用于卡发版。

## 7. 开放问题（评审时定）

1. **覆写层级**：全局配置 vs storyDefaults（同一部署不同故事对平台认知不同）——倾向先全局，故事级差异等真实需求出现再加。
2. **affordances 词表**：自由文本 vs 受控枚举（受控利于合约措辞稳定，自由利于新平台快速接入）——倾向适配器侧受控、合约侧仅展示。
3. **单平台是否注入自我认知**（她对自己"正在用的这个平台"的态度）：倾向不注入——单平台无选择场景，认知已隐含在剧本与文风里。
4. **character 文本语言**：跟随部署主语言还是随合约主语言（当前合约为英文骨架 + 中文内容混排）——倾向与 PlatformWording 的处理一致（部署侧自定，默认中文）。
